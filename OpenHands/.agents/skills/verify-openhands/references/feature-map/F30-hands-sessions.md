# F30 — Bossku Hands sessions and workflow

Bossku Hands (a fork feature) runs a coding task through a gated workflow on a local repository: plan, code, open a pull request, watch CI, repair failures, review. **Sessions** lists every Hands session with a state badge and its PR link, and a **New task** form starts one. A session page shows its state, task, the approval panel for the one pending gate, actions (Cancel, Resume, Retry, Refresh now), the PR link, CI repair rounds, why it escalated, reviewer warnings, CI failures and an event timeline. **Hands workflow** under Settings holds the approval gates, Auto Fix CI mode, budgets and per-role agent profiles. All data comes from the local Hands service at `/api/hands/*`. The session page also shows a read-only execution graph of the stages and, for a session started from a Linear issue, a Linear section. The Linear inbox and team settings (F31), the review queue and review studio (F32) and the connection status page (F33) are separate families.

Source: `src/routes/hands-sessions.tsx`, `src/routes/hands-session-detail.tsx`, `src/routes/hands-settings-workflow.tsx`, `src/components/features/hands/`, `src/components/features/sidebar/sidebar-rail-body.tsx`, `src/mocks/hands-handlers.ts`, `scripts/hands/server.mjs`.

## Sub-features

- `F30.entry-points`: the sidebar **Sessions** link (`sidebar-hands-sessions-link`) opens `/hands/sessions`; Settings navigation has **Hands workflow** (`/settings/hands-workflow`); a session row opens `/hands/sessions/<sessionId>`; starting a task navigates to its new session page.
- `F30.list`: `/hands/sessions` lists sessions (`hands-sessions-list`, one `hands-session-row-<id>` each) with a state badge and the PR link when there is one; with none it shows `hands-sessions-empty`; a failed load shows `hands-sessions-error`.
- `F30.new-task`: `hands-new-task-form` has the task text (`hands-task-input`), a local repository folder and an optional base branch; submitting starts a session and navigates to its page; a start failure shows `hands-start-error` and keeps the form.
- `F30.detail`: the session page shows the state badge, the task, the PR link (`hands-pr-link`) once a PR exists, CI repair rounds as `n of <budget>` (`hands-ci-rounds`) and the collapsed CI failures (`hands-ci-failures`) and event timeline (`hands-event-timeline`).
- `F30.approval`: while a gate is pending, `hands-approval-panel` approves exactly that gate (`approve_plan`, `open_pr` or `push_fix`); a refused approval shows `hands-approve-error`; with no pending gate there is no panel.
- `F30.actions`: **Cancel** asks for confirmation; **Resume** appears only when the session is SUSPENDED; **Retry** only when FAILED; **Refresh now** only while watching CI or ready for review; a failed action shows `hands-action-error`.
- `F30.notices`: an escalation shows a sentence with the reason (`hands-escalation`), reviewer warnings show in `hands-warnings`, a failure in `hands-failure`; READY_FOR_HUMAN_REVIEW says it is ready for a human to review (`hands-ready-notice`), never that it is merged.
- `F30.settings-form`: `/settings/hands-workflow` (`hands-workflow-form`) shows the approval-gate toggles, the Auto Fix CI radio (off, suggest, local, update_pr), CI repair budget (0 to 10, default 3), max review rounds (1 to 5), CI poll interval in seconds and an agent profile select per role (`hands-role-planner`, `hands-role-coder`, `hands-role-reviewer`).
- `F30.settings-save`: saving persists the values (`hands-settings-saved`, still there after reload); an out-of-range number or a server refusal shows `hands-settings-error`; a failed load shows `hands-settings-load-error`.
- `F30.service-down`: with the Hands service not running, the pages show their error states instead of crashing.
- `F30.graph`: the session page has a **Progress** section with `hands-execution-graph`, a read-only React Flow graph of ten stage nodes (`hands-graph-node-<stage>` for plan, approve_plan, code, review, approve_pr, open_pr, watch_ci, repair_ci, ready, merged). Each node reads done, current, waiting, failed, upcoming or skipped, and the review and repair nodes add their round counts. The wrapper is `role="img"` with an `aria-label` that names the current stage; nodes cannot be dragged, selected or focused. A COMPLETED session shows merged as done.
- `F30.linear-section`: a session started from a Linear issue shows `hands-linear-section` with the issue identifier linked to Linear and `hands-linear-sync-status`: waiting for the PR to merge, not moved to Done yet, moved to the Done state's name, or could not move it. In COMPLETED with no sync or after a failed sync, `hands-linear-retry` (**Retry Linear update**) is shown and a failure shows `role="alert"`. Without a Linear link the section is absent.

## How to get to it (user POV)

- Main sidebar **Sessions** (`sidebar-hands-sessions-link`), then a session row, or **New task** on the list page.
- Settings navigation **Hands workflow**.
- Direct URLs `/hands/sessions`, `/hands/sessions/<sessionId>` and `/settings/hands-workflow`.
- After **Start**, the app opens the new session page by itself.

## Driving it with control-openhands

Preconditions:

- Baseline state (launched, doctored, `onboard --skip` done). No LLM is needed to check the pages themselves.
- Backend dependency: the Hands service (`scripts/hands/server.mjs`, answering `/api/hands/*`) must be running. Without it every page here shows its error state (`F30.service-down`); that is the expected result, not a pass of the other rows. In a mock-mode run (MSW) sessions are served by `src/mocks/hands-handlers.ts` instead, so state transitions follow the mock, not a real repo, and a real CI or PR cannot be proved there.
- A fixture repo for real task starts: `control-openhands fixture git-repo --name qa-hands-repo`. Task text starts with `QA_`.
- Desktop viewport unless a bullet says otherwise.

- **Entry points (`F30.entry-points`).** From `/` run `control-openhands browser click 'testid=sidebar-hands-sessions-link' --expect-url '/hands/sessions(\?|$)'`. Then `control-openhands browser goto /settings/hands-workflow` and `control-openhands browser snapshot 'role=navigation'` lists **Hands workflow**. Record that these were UI entry and direct URL respectively.
- **List (`F30.list`).** On `/hands/sessions` run `control-openhands browser count '[data-testid^="hands-session-row-"]'` and `control-openhands browser snapshot 'testid=hands-sessions-list'`: each row has a state badge and, with a PR, a link. With none, `control-openhands browser text 'testid=hands-sessions-empty'` reads the empty message. `control-openhands browser screenshot --feature F30.list --name sessions`.
- **New task (`F30.new-task`).** Run `control-openhands browser fill 'testid=hands-task-input' 'QA_hands add a README line'`, fill the folder field with the fixture repo path from `control-openhands fixture git-repo`, then click the form's submit button (`control-openhands browser snapshot 'testid=hands-new-task-form'` names it) with `--expect-url '/hands/sessions/[^/]+'`. The session page opens with a state badge and the task text. A second start with an empty task or a bad folder shows `control-openhands browser text 'testid=hands-start-error'` and keeps the form.
- **Detail and approval (`F30.detail`, `F30.approval`).** On the session page `control-openhands browser snapshot 'role=main'` shows the badge, task, `hands-ci-rounds` as `n of <budget>` when CI repair has started, and the collapsed timeline. When `control-openhands browser count 'testid=hands-approval-panel'` is `1`, the panel offers the one gate named by the state (plan, PR or push fix); click its approve button and read the state badge move on (`control-openhands browser wait 'testid=hands-approval-panel' --state detached --timeout 30000`). Confirm with `control-openhands api GET /api/hands/sessions/<id>`. Do not approve a gate the panel does not show.
- **Actions (`F30.actions`).** Click **Cancel**: a confirmation appears; Cancel in it keeps the session, Confirm moves it to a cancelled state. Check **Resume**, **Retry** and **Refresh now** only in the states that offer them: `control-openhands browser count 'role=button[name="Retry"]'` is `0` unless the badge says FAILED.
- **Notices (`F30.notices`).** For an escalated or READY_FOR_HUMAN_REVIEW session, `control-openhands browser text 'testid=hands-escalation'` gives a full sentence with the reason and `control-openhands browser text 'testid=hands-ready-notice'` says ready for a human, not merged. Blocked when no session reaches those states in this run; name the missing state.
- **Settings form and save (`F30.settings-form`, `F30.settings-save`).** On `/settings/hands-workflow` run `control-openhands browser snapshot 'testid=hands-workflow-form'`: the gate toggles, Auto Fix CI radios, number fields and three role selects. Change the CI repair budget, click save, `control-openhands browser wait 'testid=hands-settings-saved' --timeout 10000`, then `control-openhands browser reload` and read the field again, and `control-openhands api GET /api/hands/settings`. Enter `11` in the budget: `control-openhands browser text 'testid=hands-settings-error'` shows a message and nothing is saved. Restore the original values afterwards.
- **Service down (`F30.service-down`).** Only on a run you own and only if the Hands service was started by this run: stop it, `control-openhands browser goto /hands/sessions`, `control-openhands browser text 'testid=hands-sessions-error'`, then `control-openhands browser errors --app-only` shows only the expected failed `/api/hands/` requests; start it again. If the service is not under this run's control, record `blocked`.
- **Graph (`F30.graph`).** On a session page, `control-openhands browser count '[data-testid^="hands-graph-node-"]'` is `10`, `control-openhands browser attr 'testid=hands-execution-graph' aria-label` names the current stage, and `control-openhands browser text 'testid=hands-graph-node-code'` gives that node's status (done, current, waiting and so on). Try to drag a node (`browser drag`): its position does not change. Blocked for a real run until a session reaches a stage other than plan; the mock serves `s-linear-active` (CODING) and `s-linear-done` (COMPLETED).
- **Linear section (`F30.linear-section`).** Preconditions: a Linear-started session (`F31`, Start session on a mapped team) or the mock session `s-linear-done`. On it, `control-openhands browser text 'testid=hands-linear-sync-status'` reads the sync state and `control-openhands browser count 'testid=hands-linear-section'` is `1`. On a session without Linear, the count is `0`. In COMPLETED with a failed sync, click `testid=hands-linear-retry` and wait for the status to change; read it back with `control-openhands api GET /api/hands/sessions/<id>` (`linear.syncedAt`, `linear.syncError`).
- **Phone.** `control-openhands browser viewport phone`, then `control-openhands browser bbox 'role=main'` for each of the three pages: `pageHorizontalOverflow` `false`. Return with `control-openhands browser viewport desktop`.

## Gotchas

- The Hands service is separate from the Agent Server; `control-openhands doctor` can say `ok` while `/api/hands/*` is down. Check `control-openhands api GET /api/hands/sessions` first.
- Mock mode (`src/mocks/hands-handlers.ts`) never opens a real PR or runs CI; rows that need a real PR link, CI rounds or an approval's repo effect are `blocked` there, not passed.
- Session ids are generated: select rows by `[data-testid^="hands-session-row-"]` plus the `QA_` task text, never a fixed id.
- Buttons shown depend on the state, so assert absence as well as presence; a missing Retry on a running session is correct.
- Never approve a gate or start a task against a repository that is not a `fixture git-repo` copy; an approval can push or open a real PR.
- Hands error texts are service-sent and not translated; assert on test ids, not wording.
- The graph always draws the same ten stages; a stage the session did not take shows `skipped` or `upcoming`, which is correct. Assert the current stage and the node count, not every label.
- The Linear section appears only for a session that came from a Linear issue; a plain `QA_` session correctly has none.
